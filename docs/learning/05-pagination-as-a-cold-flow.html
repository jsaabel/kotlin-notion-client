05 — Pagination as a cold Flow

A cursor chain that does nothing at all until somebody collects it · Medium

The hook

On 15 April 2026 a notebook example claimed pageSize(5) would fetch the first five results. It did not. journal/2026_04_15_02_Pagination_Limit_Investigation.md states the problem in two sentences:

journal/2026_04_15_02_Pagination_Limit_Investigation.md:25–28 
`pageSize(N)` controlled the *batch size* per API call, not the *total result count*. A caller who
genuinely wants only the top 5 results (e.g. a "most recently edited tasks" widget) had no way to
opt out of auto-pagination. `search()` was already single-call; `BlocksApi.retrieveChildren()`
had the same always-auto-paginate gap as `DataSourcesApi.query()`.

The interesting part is where the investigation decided the fault was not:

journal/2026_04_15_02_Pagination_Limit_Investigation.md:37–38 
- **`Pagination.kt`**: Generic helpers (`collectAll`, `asFlow`, `asPagesFlow`) are correct as-is;
  the gap is at the API layer, not in the utilities.

That verdict holds up. The Flow half already stopped early — a .take(5) ends the cursor chain after one request, and always did. What it could not do was ask for a small first request, since every flow pins pageSize to MAX_PAGE_SIZE = 100 (config/NotionApiLimits.kt:76). queryFirstPage was added alongside; the two answer different questions. This lesson is the first, and the ten lines behind it.

The concept, plainly

Everything paginated here funnels through src/main/kotlin/it/saabel/kotlinnotionclient/utils/Pagination.kt, whose central function returns a Flow<T> built by flow { }. Coldness is worth being precise about, because in a cursor chain it means four specific things.

Nothing has happened when the function returns. notion.blocks.retrieveChildrenAsFlow(id) performs zero HTTP requests. The object handed back closes over the fetcher and holds nothing else: no first page, no cursor, no connection. The chain has not started; it has been described.

The cursor is per-collection state. var cursor: String? = null lives inside the flow { } block, created fresh every time somebody collects. Two collectors mean two independent walks and two full sets of requests — this is not a stateful iterator you can pass around and pull from in pieces. It is a recipe, re-executed on demand.

The fetch loop runs in the collector's coroutine. emit is a suspend call into the collector's lambda — there is no buffer and no second thread. Page n+1 is requested only after every item of page n has been handed over and the collector has returned, so a slow consumer paces the API calls: a happy accident, given the rate limiter under all of this.

Stopping is an exception, and it lands in the right place. take(1) throws out of emit once its quota is met, unwinding the do/while loop before the next fetcher(cursor) call: the second page is never requested. Cancelling from outside — a withTimeout, a cancelled scope — cancels the fetcher while it is suspended, so the in-flight HTTP call dies with it instead of completing and being discarded. The pagination code implements neither. Both follow from the loop being ordinary sequential code inside a coroutine.

This code, annotated

The whole engine

src/main/kotlin/it/saabel/kotlinnotionclient/utils/Pagination.kt:40 
typealias PageFetcher<T, R> = suspend (cursor: String?) -> R
src/main/kotlin/it/saabel/kotlinnotionclient/utils/Pagination.kt:71–80 
    fun <T, R> asFlow(fetcher: PageFetcher<T, R>): Flow<T>
        where R : PaginatedResponse<T> =
        flow {
            var cursor: String? = null
            do {
                val page = fetcher(cursor)
                page.results.forEach { emit(it) }
                cursor = page.nextCursor
            } while (page.hasMore)
        }

T never appears on the right-hand side of the typealias — a phantom parameter, carried only so the where R : PaginatedResponse<T> constraint can tie element type to response type at the call site. That constraint is the whole abstraction: PaginatedResponse<T> (Pagination.kt:16–32) declares results, nextCursor and hasMore, and every list-shaped Notion model implements it, so one loop serves blocks, comments, users, search results and property items alike.

One detail to keep: the loop tests page.hasMore, but the value it feeds to the next iteration is page.nextCursor. A response reporting has_more: true with next_cursor: null would make it re-fetch the first page forever. The windowed drain, written later, guards exactly that — while (response.hasMore && cursor != null) (api/WindowedRowIteration.kt:91). The generic helper does not.

collectAll, and being honest about it

src/main/kotlin/it/saabel/kotlinnotionclient/utils/Pagination.kt:106–116 
    suspend fun <T, R> collectAll(fetcher: PageFetcher<T, R>): List<T>
        where R : PaginatedResponse<T> {
        val allResults = mutableListOf<T>()
        var cursor: String? = null
        do {
            val page = fetcher(cursor)
            allResults.addAll(page.results)
            cursor = page.nextCursor
        } while (page.hasMore)
        return allResults
    }

The same loop with a list where the emit was — and usually the one you want. The public surface says so: query(), list() and retrieveChildren() return List and drain the chain themselves, while the Flow variants carry an opt-in AsFlow suffix. docs/pagination.md puts the crossover near a thousand items.

Be sceptical of the memory argument especially. collectAll holds n items; the Flow holds one page — a hundred at most. For the few hundred rows most queries return that is nothing, and a caller who writes .toList() has bought the allocation back plus a wrapper. The advantages that pay are the two the loop shape gives away free: stopping early and starting work before the last page lands. If neither applies, take the list.

The flow that could not use the helper

DataSourcesApi.queryAsFlow hand-rolls the same loop, for two reasons worth reading:

That comment is the coldness caveat in practice: validation inside flow { } would not fire until first collection, possibly on another coroutine, long after the offending call. Everything above return flow { is eager; everything below is not.

src/main/kotlin/it/saabel/kotlinnotionclient/api/DataSourcesApi.kt:538–550

The second reason: it keeps emitted so the exception can carry partial results, which Pagination.asFlow, retaining nothing, could not. The sibling queryPagedFlow, needing neither, does delegate (DataSourcesApi.kt:593).

Where the cursor chain simply stops working

A single Notion query is capped at 10,000 rows server-side. At the cap the response reports has_more: false and sets request_status.type == "incomplete" — so an honest cursor loop terminates normally, and short. FOLLOWUPS.md item 26 records the shape confirmed against a live 11,000-row data source: the flag arrives on the first page, cursor still usable. The generic helper cannot see it — PaginatedResponse has no requestStatus — so query and queryAsFlow throw QueryResultLimitReached rather than return a plausible truncated list (CHANGELOG.md:661–668).

Two nested loops: the inner do/while is an ordinary cursor chain; the outer while (true) opens a fresh query — filtered from the last key value seen — whenever the previous one was truncated. New filter, new result set, new 10,000-row budget.

src/main/kotlin/it/saabel/kotlinnotionclient/api/WindowedRowIteration.kt:91–102 
                } while (response.hasMore && cursor != null)

                if (!truncated) {
                    // The window completed without hitting the cap: everything is drained.
                    return@flow
                }
                if (newRowsInWindow == 0) {
                    throw NotionException.IterationStalled(
                        keyDescription = tracker.keyDescription,
                        boundaryValue = tracker.boundaryValue,
                    )
                }

Termination is "a window finished without truncation"; newRowsInWindow == 0 is the liveness check, since a window that reopens and yields nothing new would spin forever.

Mutation enters here, and is easy to get backwards. It is not why windowing exists — the 10,000-row cap is. It is the constraint on which key you may window by:

src/main/kotlin/it/saabel/kotlinnotionclient/models/datasources/RowIterationKey.kt:12–15 
 * `last_edited_time` is deliberately not offered as a key: it changes whenever a row
 * is edited, so a row edited mid-drain moves within the ordering and can be skipped
 * or duplicated. Detecting such duplicates would require remembering every emitted
 * row id, which does not scale to the data sources this helper exists for.

Mechanically: sort ascending by last_edited_time, drain window one, and the boundary becomes the largest edit time you saw. Somebody now edits a row you emitted an hour ago. Its key jumps to now, past the boundary, so the next window's on_or_after filter matches it and you emit it twice. Any key that can move relative to a boundary you have crossed does this, in one direction or the other. Neither key on offer moves: created_time is immutable, and a unique_id is immutable and strictly increasing — which is why that one re-opens with a strict greater_than and needs no de-duplication (WindowedRowIteration.kt:193–199).

created_time pays a smaller price: Notion rounds it to the minute, so boundary ties are normal and the window reopens with on_or_after, re-reading rows already emitted.

src/main/kotlin/it/saabel/kotlinnotionclient/api/WindowedRowIteration.kt:165–175 
            return if (boundary == null || instant > boundary) {
                boundaryInstant = instant
                boundaryValue = page.createdTime
                boundaryIds.clear()
                boundaryIds.add(page.id)
                true
            } else {
                // Same created_time as the boundary (or, defensively, earlier):
                // emit only ids not already seen in this bucket.
                boundaryIds.add(page.id)
            }

boundaryIds.clear() is the line that matters: the set holds only rows sharing the current boundary timestamp and empties the moment the boundary advances, so memory is bounded by the widest one-minute bucket, not by the data source. Set.add returning false for a repeat is what makes the else branch a filter.

The same chain in TypeScript

reference/js/pagination-helpers.ts is a vendored MIT excerpt of notion-sdk-js, kept because #40 named it prior art (reference/js/README.md:12–18). Its generic helper is asFlow spelled as an async generator:

reference/js/pagination-helpers.ts:49–62 
export async function* iteratePaginatedAPI<Args extends PaginatedArgs, Item>(
  listFn: (args: Args) => Promise<PaginatedList<Item>>,
  firstPageArgs: Args
): AsyncIterableIterator<Item> {
  let nextCursor: string | null | undefined = firstPageArgs.start_cursor
  do {
    const response: PaginatedList<Item> = await listFn({
      ...firstPageArgs,
      start_cursor: nextCursor,
    })
    yield* response.results
    nextCursor = response.next_cursor
  } while (nextCursor)
}

Structurally identical, and note it loops on the cursor rather than on has_more — the guard the Kotlin helper lacks. The idiomatic differences are the interesting part. An async generator is single-shot and stateful: the iterator is the cursor position, so you can pull ten rows, put it down, and pull ten more later. A cold Flow cannot be half-consumed and set aside — that means a channel and a parked coroutine in Kotlin — but it can be collected twice, composed with operators, and cancelled from outside. Breaking out of a for await ends the generator between yields; aborting a request already in flight needs an AbortController threaded through by hand. Structured cancellation reaches the socket for free; resumable position costs extra. JavaScript made the opposite trade.

The drains diverge more sharply. Both partition by created_time ascending, restart from the last-seen boundary on incomplete, and de-duplicate ties — arrived at independently here, with this excerpt as the confirmation (reference/js/README.md:53–60). But the JS version de-duplicates against every row it has ever yielded:

reference/js/pagination-helpers.ts:169, 192–195 
  const seenRowIds = new Set<string>()
// …
        if (!seenRowIds.has(row.id)) {
          seenRowIds.add(row.id)
          yield row
        }

For a data source large enough to need this helper, that set ends up holding every id in it. The Kotlin tracker keeps only the boundary bucket — and RowIterationKey's KDoc, quoted above, rejects the unbounded set in the same breath as last_edited_time. The JS helper also offers created_time only, throwing a string Error when one timestamp holds more rows than the cap; this repo adds the UniqueId key as the escape hatch, and a typed IterationStalled pointing at it.

The analogy, and its limits

Sequence is the analogy that almost works, and it is worth knowing where it breaks. Cold, lazy, pull-based, take stops the producer mid-generation — true of both. It breaks on one annotation: SequenceScope is @RestrictsSuspension, so inside sequence { } you may call yield and nothing else that suspends. A page fetcher is a suspend function making a network call. No version of asFlow written with sequence { } avoids blocking a thread per page. That restriction, not reactive-streams enthusiasm, is why the return type is Flow.

The Java Stream intuition misleads differently. A Stream is single-use and its laziness optimises over a source that already exists; re-running it throws. A cold Flow is multi-use by design and each use re-executes the side effects — here, the whole cursor chain. Collecting twice is not a caching bug, it is two complete walks of the API.

One limit on the Flow story itself: this is not a concurrency mechanism. Nothing runs ahead. Page n+1 is not fetched while you process page n, and no operator in Pagination.kt makes it so. .buffer() buys exactly one page of look-ahead — at which point you have chosen to run ahead of a rate limiter that exists to stop you. Sequential is the right default here, not an oversight.

Exercises

Exercise 1 — Verifiable

Serve a three-page cursor chain from MockEngine, collect one item, and prove the other two pages were never requested. Use the repo's builder in src/test/kotlin/unit/util/MockResponseBuilder.kt: handlers are tried in order and the first non-404 wins, so the cursor-specific ones must be registered before the catch-all. Create src/test/kotlin/unit/utils/ScratchColdFlowProbe.kt:

package unit.utils

import io.kotest.core.annotation.Tags
import io.kotest.core.spec.style.FunSpec

@Tags("Unit")
class ScratchColdFlowProbe :
    FunSpec({

        fun blockPage(
            id: String,
            nextCursor: String?,
            hasMore: Boolean,
        ): String {
            val cursor = nextCursor?.let { "\"$it\"" } ?: "null"
            return """
                {
                  "object": "list",
                  "results": [
                    {
                      "object": "block",
                      "id": "$id",
                      "created_time": "2026-01-01T00:00:00.000Z",
                      "last_edited_time": "2026-01-01T00:00:00.000Z",
                      "in_trash": false,
                      "parent": {"type": "page_id", "page_id": "parent-1"},
                      "has_children": false,
                      "type": "paragraph",
                      "paragraph": {"rich_text": []}
                    }
                  ],
                  "next_cursor": $cursor,
                  "has_more": $hasMore,
                  "type": "block",
                  "block": {}
                }
                """.trimIndent()
        }

        test("take(1) fetches exactly one page of the cursor chain") {
            runTest {
                val http =
                    mockClient {
                        addJsonResponse(HttpMethod.Get, "start_cursor=c-2", blockPage("b-3", null, hasMore = false))
                        addJsonResponse(HttpMethod.Get, "start_cursor=c-1", blockPage("b-2", "c-2", hasMore = true))
                        addJsonResponse(HttpMethod.Get, "/v1/blocks/", blockPage("b-1", "c-1", hasMore = true))
                    }
                val engine = http.engine as MockEngine
                val notion = NotionClient.createWithClient(http, NotionConfig("test-token"))

                val ids = notion.blocks.retrieveChildrenAsFlow("block-1").take(1).toList().map { it.id }

                ids shouldBe listOf("b-1")
                engine.requestHistory.size shouldBe 1

                val all = notion.blocks.retrieveChildrenAsFlow("block-1").toList().map { it.id }

Expected end state. ./gradlew test -Dkotest.tags.include="Unit" --tests "*.ScratchColdFlowProbe" goes green. engine.requestHistory.size shouldBe 1 is the assertion the exercise is for: pages two and three exist in the mock and were never asked for. The rest is the other half of coldness — collecting the same Flow again re-walks the chain, taking the running total to four, not three. Now break it: replace .take(1) with .first(), then with .toList().take(1), predicting each request count before running. Delete the file afterwards.

Exercise 2 — Extension

CHANGELOG.md:377 heads the feature "Resumable iteration past the 10,000-row pagination ceiling". It resumes across windows; nothing survives the process. Design the version that does.

First, the state. For RowIterationKey.UniqueId it is one Int — lastNumber at WindowedRowIteration.kt:189 — and the strict greater_than window makes a restart from it exactly correct. For CreatedTime it is a timestamp and boundaryIds; drop the set and the resume re-emits the whole boundary minute. Bounded, not constant, different per key.

Then the real question: API shape. RowIterationKey is a public sealed interface naming which column to window by; the boundary is private mutable state on an internal tracker. Does the checkpoint belong on the key — CreatedTime carrying an optional boundary, and so no longer a data object — or in a separate parameter and return value, leaving the key a pure column selector? Adding a field to a public sealed hierarchy is source-breaking for anyone with an exhaustive when, so this is a compatibility decision, not a naming one. Sketch both.

Finally, what are you promising? The drain is already not a snapshot (DataSourcesApi.kt:678–683), and one resumed a day later is weaker again: rows created behind your boundary meanwhile are never seen, and a unique_id backfill finished overnight silently changes what the window matches. Is a checkpoint that cannot state its own staleness a feature or a trap?
