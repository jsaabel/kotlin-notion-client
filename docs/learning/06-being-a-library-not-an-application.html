06 — Being a library, not an application

Every public name is a promise, and you cannot see who is holding you to it · Medium

The hook

Most library READMEs open with badges. README.md opens with a warning:

README.md:5–11 
> **⚠️ AI-Assisted Development Notice**
> This library is developed primarily by AI agents (Claude Code) under human direction. While it includes comprehensive testing (1,200+ unit tests), validation against official Notion API samples, and live-API integration passes, please be aware of potential issues:
> - Documentation examples may not perfectly match implementation
> - Edge cases may exist that weren't covered in testing
> - Some API patterns may have inconsistencies
>
> We are deliberately open about this — including when it bites: several fixes in the upcoming 0.6.0 release correct bugs that earlier AI-assisted releases introduced (see [CHANGELOG.md](CHANGELOG.md)).

The changelog says it again, longer, with issue numbers attached:

CHANGELOG.md:23–27 
live-API verification pass (#61) against a real workspace. That openness cuts both ways:
several fixes in this release correct bugs that earlier, equally AI-assisted releases
introduced — most seriously a timezone bug where offset-less datetimes were silently stored

whose payloads never reached the wire. The live verification pass exists precisely because

At face value that is a statement about publishing, not about AI: once an artifact is on Maven Central, fixing a bug and breaking a caller are often the same physical act. 0.6.0 shipped on 2026-09-03 (CHANGELOG.md:12), the installation snippet tells you to depend on it (README.md:30), and gradle.properties:6 already reads version=0.7.0-SNAPSHOT. "The upcoming 0.6.0 release" is a released one now, downloadable by strangers — and nothing in this repository can tell you how many of them wrote an exhaustive when over Icon.

The concept, plainly

In an application the compiler sees every call site: rename a field and the build either goes green or hands you the list of repairs. A published library inverts that. The compiler sees the call sites that do not matter — your own tests and samples — and none of the ones that do. The discipline replacing "recompile everything" is deciding in advance what you will be held to.

Four constraints get collapsed into the word "breaking". They are independent:

Visibility — what a consumer can name at all. Anything public is part of the deal whether you meant it or not; anything internal is yours to change on a whim.

Source compatibility — their code still compiles. Adding a variant to a sealed hierarchy breaks this: an exhaustive when without else no longer does.

Binary compatibility — their already-compiled jar still links, without recompilation. Adding a property to a public data class breaks this while leaving source compatibility intact: the primary constructor and the synthetic copy$default both change JVM descriptors, so an old caller meets NoSuchMethodError even though recompiling its unchanged source would have succeeded.

The promise — what your version number and changelog say you will do. Social, not mechanical, and the only one a user can read in advance.

Neither of the middle two implies the other, and a change can dodge both and still break someone. When SearchFilter.property stopped defaulting to "object" (CHANGELOG.md:162–168) no signature moved: Kotlin compiles default arguments into the callee, so an old jar calling SearchFilter(inTrash = true) links perfectly and silently sends a different payload — a break no compiler on either side will mention.

And one structural fact explains why a library needs tooling an application does not. Your test suite compiles from source, in the same build, against the classes it tests. It is not unlikely to catch a binary break; it is incapable of it. So is ./gradlew build. The only observer who can see one is a consumer who did not recompile.

This code, annotated

A variant added to a sealed hierarchy

ADR-0002 adds two write-only sentinels so an intended JSON null is carried by a value rather than a Kotlin null. Its Consequences section states the cost, then bounds it:

docs/adr/0002-explicit-null-payloads.md:104–107 
- `Icon` and `PageCover` gain a variant. Both are sealed and public, so an exhaustive `when`
  over them in user code stops compiling. In this repo nothing matched exhaustively —
  `RequestValidator` and `PendingUploadResolver` both test `is …PendingUpload` and are
  unaffected.

The variant:

src/main/kotlin/it/saabel/kotlinnotionclient/models/base/Icon.kt:130–133 
    @Serializable(with = IconRemovedSerializer::class)
    data object Removed : Icon() {
        override val type: String = "removed"
    }

Walk the blast radius rather than assuming it. A consumer's exhaustive when (icon) with no else now fails to compile; one with an else, or an if chain of is checks, is untouched. A jar compiled against 0.5.0 links fine and cannot even hit the latent NoWhenBranchMatchedException: the sentinel is write-only, produced by icon.remove() and never by decoding (CHANGELOG.md:198–200). Source-only, then, and only for callers who took the exhaustiveness Kotlin offered them.

And it was not a one-off: 0.6.0 widened six closed types this way — FileUploadStatus, FileUploadError, FormulaResult, RollupResult, Icon and PageCover (CHANGELOG.md:119–124, :126–130, :138–139, :144–147, :198–200) — each with an explicit Migration: line. The project does not avoid the break; it prices it. The instinct predates the agents: IDEAS.md row 2 parks a "breaking rename" for "before the 0.4.0 release".

Which is defensible, because there is no deprecation cycle for this. @Deprecated marks a declaration you can stop using; it cannot express "a when you already wrote will need another arm". The softenings are structural and must be chosen in advance — and one is already here. The Unknown fallbacks exist so that "any future formula.type/rollup.type Notion adds now degrades to Unknown" (CHANGELOG.md:148–150). A hierarchy with a documented catch-all teaches callers to write else, and callers who write else do not break: usually read as a deserialization safety net, equally a compatibility one.

internal, and the thirteen serializers that missed it

The rate limiter is the cleanest use of visibility here — the bucket is an implementation detail and is marked as one:

src/main/kotlin/it/saabel/kotlinnotionclient/ratelimit/TokenBucket.kt:26–30 
internal class TokenBucket(
    private val sustainedRate: Double,
    private val burstCapacity: Int,
    private val currentTimeMillis: () -> Long = { System.nanoTime() / 1_000_000 },
) {

while RateLimitConfig — the thing a caller tunes — stays public. Better still, the plugin's config class is public but carries a member that is not:

src/main/kotlin/it/saabel/kotlinnotionclient/ratelimit/NotionRateLimit.kt:25–29 
    /**
     * Test seam: overrides the token bucket's millisecond time source so tests can drive pacing
     * with `kotlinx.coroutines.test` virtual time. `null` uses a real monotonic clock.
     */
    internal var timeSourceMillis: (() -> Long)? = null

Exactly what internal is for: a seam the tests need (src/test/kotlin/unit/ratelimit/RetryAfterPluginTest.kt:84 sets it), owed to no consumer.

Elsewhere the line falls where it happened to fall. Of 429 top-level type declarations under src/main/kotlin, 26 are internal. One category shows the arbitrariness: thirteen top-level serializer objects are public and fifteen are internal, doing the same job. The telling pair belongs to one model — IconSerializer is public (models/base/IconSerializer.kt:30) while IconRemovedSerializer, for a nested variant of that same class, is internal (models/base/Icon.kt:167). A serializer named only inside @Serializable(with = …) is an implementation detail by construction; publishing it promises its name and behaviour to people with no reason to want either.

One habit keeps that invisible. Forty of the hundred files under src/main/kotlin open with exactly @file:Suppress("unused"), thirty-four of them among the sixty-six in models/. It is not wrong — most public declarations in a library legitimately have no in-repo caller — but it is file-wide and permanent , and "nothing here names this declaration" is exactly the signal that would have flagged those thirteen serializers.

What actually ships

The dependency block is unusually thoughtful about it — most projects never write this comment down:

build.gradle.kts:20–31 
dependencies {
    // API dependencies: these types appear in the library's public signatures, so they must be
    // on consumers' compile classpath (`api` publishes as Maven `compile` scope, `implementation`
    // as `runtime` — which leaves callers unable to compile against the typed overloads).
    api(libs.kotlinx.datetime) // LocalDate/LocalDateTime/TimeZone in date builders and accessors
    api(libs.kotlinx.serialization.json) // JsonElement/JsonObject in view, block and database models
    api(libs.kotlinx.coroutines.core) // Flow<T> returned by the *AsFlow/*PagedFlow pagination helpers

    // Implementation dependencies: internal only, not exposed in public signatures
    implementation(libs.ktor.client.core)
    implementation(libs.bundles.ktor)
    implementation(libs.bundles.logging)

The last line is where the application habit survives. That bundle is two artifacts:

gradle/libs.versions.toml:50 
logging = ["slf4j-api", "logback-classic"]

logback-classic is a logging backend, and implementation publishes it at Maven runtime scope — so every consumer gets Logback on their runtime classpath, where SLF4J binds whichever backend it finds first. Picking the backend is the application's call; a library ships the facade at most. Here not even that is used: grep -rn "org.slf4j\|LoggerFactory" src/main/kotlin returns nothing. The client logs through Ktor with a hand-rolled logger:

src/main/kotlin/it/saabel/kotlinnotionclient/NotionClient.kt:167–172 
                            logger =
                                object : Logger {
                                    override fun log(message: String) {
                                        println(message)
                                    }
                                }

Opt-in, so defensible (installed only when config.logLevel != LogLevel.NONE, NotionClient.kt:165) — but the checklist at journal/2025_10_15_Maven_Central_Publishing_Setup.md:362 asks for "No Debug Code: Remove println statements", and this is a library writing to a consumer's stdout while shipping an unused Logback.

The publication config is tidy, and one conditional carries the local workflow:

build.gradle.kts:116–119 
    // Sign all publications with GPG — skipped for local publishing (./gradlew publishToMavenLocal -PskipSigning)
    if (!project.hasProperty("skipSigning")) {
        signAllPublications()
    }

Central requires signatures; a local smoke test does not, and needing a GPG key to try your own artifact is what stops people testing releases. Dokka is applied bare (build.gradle.kts:5) — enough for the dokkaJavadocJar Central wants.

What the version number promises

CHANGELOG.md:6 says the project "adheres to Semantic Versioning", which at 0.x mostly disclaims: clause 4 says anything may change at any time and the API should not be considered stable. The repo behaves accordingly — 0.6.0 is a breaking minor — and neither README.md nor CONTRIBUTING.md states a stability policy, a support window or a route to 1.0.0.

What is promised is not stability but disclosure, and the README notice is its strong form: an API document naming the failure modes of its own construction before you adopt it. It costs the impression of solidity — no rival README volunteers "some API patterns may have inconsistencies" — and buys a reader who knows what to check. The accounting behind it is real; one FOLLOWUPS.md row catches the version question at the right moment:

FOLLOWUPS.md:77 
| 37 | run-wide | **Three source-breaking changes landed on this branch** (#36 sealed-class additions, #39 `StatusConfiguration.options`, #42 `DatabaseProperty.Formula.formula`). All are captured in the batched CHANGELOG entry. Confirm the version bump reflects them before release. | filed (#62) |

Note what it counts: three source-breaking changes, found by agents reading their own diffs. No mechanism counted them, and none is a binary break. That is the gap where binary-compatibility-validator would sit — it is not in the plugins block (build.gradle.kts:3–10), and adopting it is yours to weigh, not a task here. What it does is narrow. apiDump writes a human-readable .api file listing every public and protected JVM declaration; apiCheck, wired into check, fails the build when the compiled surface stops matching it. It has no opinion about whether a change is good — it turns "the ABI changed" into a diff you must review in the same commit, which is the one thing the compiler and the tests structurally cannot give you. On Kotlin 2.3.21 (gradle/libs.versions.toml:5) it needs no separate plugin; the Kotlin Gradle plugin has carried the validation natively since 2.2. The objection: at 0.x, breaking deliberately each release, the file is one more artifact to regenerate. The answer: regenerating it is precisely when you would notice a break you had not priced.

The analogy, and its limits

internal reads like Java's package-private, and day to day it does: usable by nearby code, invisible to consumers. Three places it stops mapping:

The unit is the compilation, not the package. internal spans the whole main source set, so TokenBucket is reachable from every package here and none outside — a publish/don't-publish switch, not a layering tool.

Tests are inside it. The Kotlin Gradle plugin associates the test compilation with main, which is why RetryAfterPluginTest.kt:84 can set an internal var from another package. So marking something internal will not break your test compilation: compileKotlin is the only signal.

The JVM does not enforce it. An internal class compiles to a public class file and internal functions get name-mangled with the module name; a determined Java consumer can call both. It states what you will support, not what you have locked — which is why a tool that records the surface adds something a keyword cannot.

And one analogy to distrust outright: "0.x means nothing is stable, so nothing is my problem". The version governs when you may break the API, not whether you must know what it is.

See it yourself

Look at the contract you publish, not the one in the build script:

./gradlew generatePomFileForMavenPublication
grep -B2 -A3 "logback" build/publications/maven/pom-default.xml

Thirteen dependencies, Logback among them at runtime scope. Then measure the surface itself:

grep -rhE '^(public |internal |abstract |open |sealed |data |value |enum |annotation |fun )*(class|interface|object) ' src/main/kotlin --include=*.kt | wc -l
grep -rhE '^internal (abstract |open |sealed |data |value |enum |annotation |fun )*(class|interface|object) ' src/main/kotlin --include=*.kt | wc -l

Exercises

Exercise 1 — Verifiable

Mark a public type internal and let the compiler map what depends on it — twice, reverting each edit with git checkout -- <file>.

Run A. Put internal in front of object IconSerializer at src/main/kotlin/it/saabel/kotlinnotionclient/models/base/IconSerializer.kt:30 and run ./gradlew compileKotlin. Expected end state: BUILD SUCCESSFUL, zero errors — an @Serializable(with = …) reference is not a signature, so nothing leaks. The silence is the finding.

Run B. Do the same to data class FileUploadProgress at src/main/kotlin/it/saabel/kotlinnotionclient/models/files/FileUploadProgress.kt:8. Expected end state: exactly two errors, both in that file (paths trimmed):

e: …/models/files/FileUploadProgress.kt:66:20 'public' function exposes its 'internal' parameter type 'FileUploadProgress'.
e: …/models/files/FileUploadProgress.kt:87:9 'public' function exposes its 'internal' parameter type 'FileUploadProgress'.

Those two lines are the type's public reach: UploadProgressCallback and FileUploadResult.Failure.partialProgress, and nothing else in a hundred files. Now repeat it on something load-bearing — models/base/Icon.kt:31 is a good scare — predicting the error count first. The caution underneath: making a published type internal is itself a source break, and this decision's window is before publication.

Exercise 2 — Extension

ADR-0002 lists four rejected alternatives (docs/adr/0002-explicit-null-payloads.md:78–96); a deprecation cycle is not among them, and the source break appears only in Consequences, noted rather than decided. Write the amendment that treats it as a decision.

Sketch the staged version: what ships in 0.6.0 if Icon.Removed may not appear yet? Candidates worth costing — a separate IconUpdate type used only by request builders, leaving Icon untouched; the sentinel plus a documented "always write an else"; or a @Deprecated shim, worth proving cannot exist rather than assuming it.

Then price them. How many releases does the cycle span at this cadence, and who is protected? Concretely: a consumer with an exhaustive when over Icon, pinned to 0.5.0. What would they do differently given a deprecation warning rather than a compile error plus a Migration: line?

Finally: at 0.x semver already permits the hard break, so a deprecation cycle is a promise stronger than your version number makes. Decide whether to start making it before 1.0.0, and what triggers it — every sealed hierarchy, or only those a consumer plausibly matches on. That rule, not this one ADR, is the deliverable.
