03 — Type-safe builders, and why five authors got the DSL wrong

Builder.() -> Unit, the arity convention, and the affordance underneath · Easy–medium

The hook

docs/adr/0003-dsl-nesting-and-parent-addressing.md was accepted on 22 August 2026, and its Context section is one of those rare bug reports where the evidence does all the arguing:

docs/adr/0003-dsl-nesting-and-parent-addressing.md:12–20 
**Nesting.** Collection-shaped nesting takes a lambda — `properties { … }`, `content { … }`,
`files { … }`, `richText { … }`. Single-value nesting takes a receiver property —
`icon.emoji("📄")`, `parent.dataSource(id)`. That split is defensible, but it was never written
down, and the evidence says nobody infers it: **twenty snippets across the repo wrote the lambda
form for a single-value builder, and none of them compiled.** Six were user-facing
(`README.md`, `QUICKSTART.md`, `docs/notebooks.md`, `docs/rich-text-dsl.md`,
`docs/data-sources.md`), fourteen were KDoc, and two of those fourteen were *runtime error
messages* telling a user to write `icon { upload(id) }` — a repair instruction that does not
compile. Five separate authoring passes independently reached for the lambda.

The clause that stops being about a DSL is the last one: five separate authoring passes independently reached for the lambda. Not one careless author — five passes, months apart, across README prose, quickstart docs and the KDoc on the builders themselves, each written by somebody who had the source open.

The two runtime error messages are the artefact worth seeing whole. src/main/kotlin/it/saabel/kotlinnotionclient/models/base/Icon.kt holds a serializer that refuses to encode an icon whose file has not been uploaded yet, and hands the caller a remedy string. Before the ADR, that remedy read:

Ten months of accrual between that entry and the ADR that closed it, and in those ten months the count went up.

The concept, plainly

A function type with receiver — Builder.() -> Unit — is the entire mechanism a Kotlin DSL runs on. It is an ordinary one-argument function whose argument is bound as this inside the body instead of being named. On the JVM it compiles to Function1<Builder, Unit>; the receiver is the parameter, and the difference is purely in how the compiler resolves unqualified names in the body. That is why emoji("📄") inside a block resolves to a method on a builder the caller never mentions.

Which gives every DSL in this repository the same three-part shape: construct a builder, run the caller's block against it as receiver, ask it for the immutable request object. Builder().apply(block).build() is that shape written on one line, and it recurs often enough here that it is worth recognising as a single idiom rather than three calls. The builder is mutable and throwaway; the thing it returns is a @Serializable data class that goes on the wire.

The design question a builder DSL then has to answer, over and over, is what shape does a nested builder take at the call site — and this repository's answer, which ADR 0003 finally wrote down, is that the shape follows the arity of the thing being built:

docs/adr/0003-dsl-nesting-and-parent-addressing.md:43–48 
- **Collection-shaped nesting takes a lambda.** `properties`, `content`, `files`, `richText`.
  There is no receiver-property form and there should not be: the braces group many calls.
- **Single-value nesting supports both.** Every single-value nested builder now exposes a `val`
  *and* a same-named `fun` taking a lambda. A `val` and a `fun` of the same name coexist in
  Kotlin without a JVM signature clash — they live in different namespaces — so this is purely
  additive.

Note what the second bullet is not. It is not "we picked the better form". It is "we kept the form we teach and stopped punishing the form people reach for", which is a different kind of decision — a concession to observed behaviour rather than an argument won. The docs still teach icon.emoji("📄"), on the grounds that braces around a single call are noise (lines 58–62 of the same ADR). The lambda exists so that being wrong costs nothing.

This code, annotated

The idiom, in one line and in four

src/main/kotlin/it/saabel/kotlinnotionclient/models/datasources/DataSourceQueryBuilder.kt:36 
fun dataSourceQuery(builder: DataSourceQueryBuilder.() -> Unit): DataSourceQueryRequest = DataSourceQueryBuilder().apply(builder).build()

Everything is in that signature. apply takes a T.() -> Unit and returns its receiver, so .apply(builder) is exactly "run the caller's block against a fresh builder"; .build() converts. The same thing written out:

src/main/kotlin/it/saabel/kotlinnotionclient/models/pages/CreatePageRequestBuilder.kt:626–630 
fun createPageRequest(block: CreatePageRequestBuilder.() -> Unit): CreatePageRequest {
    val builder = CreatePageRequestBuilder()
    builder.block()
    return builder.build()
}

builder.block() is the call that binds the receiver. A function type with receiver is invoked like an extension function, and that is the only syntax you need to know to write one of these from scratch.

Collection nesting: a lambda, and only a lambda

src/main/kotlin/it/saabel/kotlinnotionclient/models/pages/CreatePageRequestBuilder.kt:184–188 
    fun properties(block: PagePropertiesBuilder.() -> Unit) {
        val builder = PagePropertiesBuilder()
        builder.block()
        properties.putAll(builder.build())
    }

The idiom again, one level down, with putAll instead of a return. There is no val properties beside it, deliberately: the braces earn their place by grouping many calls, and a properties.title("Name", "x") chain would put a dot in front of every property on a page.

Single-value nesting: the val and the fun

src/main/kotlin/it/saabel/kotlinnotionclient/models/pages/CreatePageRequestBuilder.kt:92–107 
    /**
     * Builder for icon configuration.
     */
    val icon = IconBuilder()

    /**
     * Configures the icon in a lambda, as an alternative to the `icon.xxx()` receiver form.
     *
     * Both forms drive the same builder and are last-call-wins; see
     * [docs/dsl-conventions.md](https://github.com/jsaabel/kotlin-notion-client/blob/main/docs/dsl-conventions.md).
     *
     * @param block Configuration block applied to the icon builder
     */
    fun icon(block: IconBuilder.() -> Unit) {
        icon.block()
    }

Four lines of implementation across the pair, and icon.block() is the same receiver-binding call as before — this time against the long-lived val rather than a fresh instance, which is what makes the two forms interchangeable rather than merely similar. Both mutate the same IconBuilder, so both are last-call-wins, and mixing them in one request is legal if pointless. docs/dsl-conventions.md:50–59 states this as the rule new builders follow.

The ADR's justification for the pair is a claim about namespaces, and it is checkable. Compile the module and disassemble:

javap -p build/classes/kotlin/main/it/saabel/kotlinnotionclient/models/pages/CreatePageRequestBuilder.class
// …
  private final it.saabel.kotlinnotionclient.models.pages.CreatePageRequestBuilder$IconBuilder icon;
  public final it.saabel.kotlinnotionclient.models.pages.CreatePageRequestBuilder$IconBuilder getIcon();
  public final void icon(kotlin.jvm.functions.Function1<? super it.saabel.kotlinnotionclient.models.pages.CreatePageRequestBuilder$IconBuilder, kotlin.Unit>);
// …

Three members, no collision, for two reasons stacked on each other. The property's JVM name is getIcon, not icon, so it never meets the function; the backing field is called icon, and does not clash with the method because fields and methods are separate namespaces in the class file. On the Kotlin side it is simpler still: icon { … } is a call, resolved in the function namespace, and icon.emoji(…) is a property access. Being additive is not a lucky accident of this one name.

Where the nested builder writes to

src/main/kotlin/it/saabel/kotlinnotionclient/models/pages/CreatePageRequestBuilder.kt:320–329 
    @PageRequestDslMarker
    inner class IconBuilder {
        /**
         * Sets an emoji icon.
         *
         * @param emoji The emoji character(s)
         */
        fun emoji(emoji: String) {
            this@CreatePageRequestBuilder.iconValue = Icon.Emoji(emoji = emoji)
        }

inner, so the nested builder holds a reference to the outer one and can assign iconValue through a qualified this. It stores nothing itself; it is pure syntax, a namespace with side effects. That matters for the interchangeability above — because the state lives on the outer builder, it makes no difference whether you reached emoji through the val or through the lambda.

@DslMarker, and what it actually restricts

src/main/kotlin/it/saabel/kotlinnotionclient/models/views/ViewRequestBuilder.kt:5–10 
/**
 * DSL marker for View request builders. Prevents nested builder calls from leaking into
 * outer builder scopes.
 */
@DslMarker
annotation class ViewRequestDslMarker

An annotation class annotated @DslMarker becomes a scope-control marker: when two implicit receivers in scope carry markers of the same annotation class, only the innermost is available without qualification. It is not one marker for the codebase. grep -rn "DslMarker" src/main finds thirteen files declaring thirteen marker annotations — PageRequestDslMarker, PagePropertiesDslMarker, RichTextDslMarker, DatabaseRequestDslMarker and so on, each covering one builder family. Four builder files carry no marker at all, DataSourceQueryBuilder.kt and PageContentBuilder.kt among them.

That per-family split has a consequence that is easy to miss and easy to check. Within a family the marker bites: createPageRequest and its IconBuilder both carry PageRequestDslMarker, so an outer call made from inside icon { } is rejected. Across families it does not: PagePropertiesBuilder carries a different marker, so from inside properties { } the whole page builder is still implicitly in scope, and this compiles today —

createPageRequest {
    parent.dataSource("ds")
    properties {
        title("Name", "x")
        icon.emoji("📄")     // outer receiver, reached from the properties block
    }
}

— which is precisely the leak the annotation exists to prevent, one level out. Worth knowing before treating the markers as blanket protection. And even inside a family the restriction is narrow by design: it removes the implicit receiver only. Capture the outer builder in a local and call through it explicitly and the compiler is content, because you have said which receiver you meant, which was the whole complaint.

The test that keeps the documentation honest

src/test/kotlin/unit/dsl/DocumentedSnippetsTest.kt:85–105 
            it("is accepted everywhere the receiver form is, and agrees with it") {
                val receiverForm =
                    createPageRequest {
                        parent.dataSource("data-source-id")
                        icon.emoji("📄")
                        cover.external("https://example.com/cover.png")
                        template.none()
                        position.pageEnd()
                    }

                val lambdaForm =
                    createPageRequest {
                        parent { dataSource("data-source-id") }
                        icon { emoji("📄") }
                        cover { external("https://example.com/cover.png") }
                        template { none() }
                        position { pageEnd() }
                    }

                lambdaForm shouldBe receiverForm
            }

Two assertions in one: that both forms compile — which is what a source file can assert and a Markdown fence cannot — and that they produce equal requests. The file's own header calls this out: it "holds the documented conventions as real code so that a builder change which would falsify a README snippet fails the build instead of the reader" (lines 25–27). That is the structural fix. Deprecating the old spellings fixed the twenty snippets; this test is what stops the twenty-first.

The analogy, and its limits

The closest familiar thing is Gradle's Kotlin DSL, and the mapping is exact rather than evocative. dependencies { } is a method taking a function type with receiver; implementation(…) inside it resolves against a receiver nobody wrote down. Gradle has the same asymmetry between block-shaped and property-shaped configuration, taught by convention rather than by the compiler.

The analogy that misleads is the classical Java builder — new Builder().icon(x).build(). It looks like the same pattern in different syntax, and it is not, in the one way that decides this design. A chained Java builder has a single flat namespace: every method is a method on the one builder, so icon can only be a method and the question this ADR is about cannot arise. Nesting is what buys scoped namespaces — emoji means something only inside an icon — and scoped namespaces are what create a choice of shape at each call site, and therefore the possibility of choosing inconsistently. The chaining style also returns the builder from every call, which is why DataSourceQueryBuilder's methods return DataSourceQueryBuilder while CreatePageRequestBuilder's return Unit.

Which brings the actual point. Five careful passes reached for a form that did not exist, and the fix was to make it exist. That inversion is the transferable part of this ADR and it is not about DSLs at all. When competent users converge on the same wrong usage, the wrong thing is the affordance. The alternative reading — that five authors were each individually sloppy — requires believing something less likely than "braces after a name look callable". Every API you own emits a guess about how to use it, through its shape rather than its documentation, and the reliable way to learn what that guess is, is to notice what people write when they are not looking it up. Twenty uncompiled snippets are an unusually clean measurement of that, because nobody was trying to measure anything.

See it yourself

Start with the guarantee. No network, about a second:

./gradlew test -Dkotest.tags.include="Unit" --tests "*.DocumentedSnippetsTest"

Then break it on purpose — which for a DSL means a compile error, not a red test. Create src/test/kotlin/unit/dsl/ScratchProbe.kt:

package unit.dsl

import it.saabel.kotlinnotionclient.models.pages.createPageRequest

fun probe() {
    createPageRequest {
        parent.dataSource("ds")
        icon {
            title("Leaked outer call")
        }
    }
}

title is a method on the outer CreatePageRequestBuilder; both receivers carry PageRequestDslMarker. Run ./gradlew compileTestKotlin:

e: file:///home/user/kotlin-notion-client/src/test/kotlin/unit/dsl/ScratchProbe.kt:9:13 'fun title(titleText: String): Unit' cannot be called in this context with an implicit receiver. Use an explicit receiver if necessary.

That last sentence is the annotation describing its own scope. Take it at its word: bind the outer builder to a local, call outer.title(…) from inside the same icon { } block, and it compiles. Now swap the probe body for the cross-family case from earlier — properties { title("Name", "x"); icon.emoji("📄") } — and it compiles too, with no marker error, because the two builders carry different markers. Delete the file when you are done.

Exercises

Exercise 1 — Verifiable

Reproduce the compile error the twenty snippets produced, and read what it actually said. Every single-value builder in the repo now exposes both forms, so the pre-ADR shape has to be rebuilt — fifteen lines will do it, in a scratch file at src/test/kotlin/unit/dsl/ScratchProbe.kt:

package unit.dsl

class PreAdrBuilder {
    class IconBuilder {
        fun emoji(emoji: String) = Unit
    }

    val icon = IconBuilder()
}

fun probeD() {
    PreAdrBuilder().apply {
        icon { emoji("📄") }
    }
}

Expected end state. ./gradlew compileTestKotlin fails with exactly two errors on the icon { emoji("📄") } line, and the first is the one worth staring at:

e: file:///home/user/kotlin-notion-client/src/test/kotlin/unit/dsl/ScratchProbe.kt:13:9 Unresolved reference 'icon'.
e: file:///home/user/kotlin-notion-client/src/test/kotlin/unit/dsl/ScratchProbe.kt:13:16 Unresolved reference 'emoji'.

Unresolved reference icon — while val icon sits four lines above, in scope, spelled identically. icon { … } is a call, so it is looked up in the function namespace, and the property is not a candidate; the compiler cannot even see the thing you meant, so it offers no hint about the dot. Then predict, before running, what properties.title("Name", "x") does inside a real createPageRequest { } — the mirror mistake, made against a collection builder that will never have a receiver form. Check it. The answer involves a private field and is worse than you expect.

Exercise 2 — Extension

Sketch the repo-wide @DslMarker migration. Today there are thirteen markers, one per builder family, plus four unmarked builder files; the demonstration above shows what that buys and what it lets through. The obvious move is one @NotionDsl annotation applied everywhere.

Work out what it would reject that is currently legal and reasonable. Start with the case that compiles today: is properties { … icon.emoji("📄") } a leak worth forbidding, or a convenience someone is relying on? Then look for the places where crossing a family boundary is the point — a rich text block built inside a page property, inside a content block, inside a page request is three or four nested receivers deep, and unifying the markers makes every outer one unreachable at once. Is there a legitimate call that becomes unwritable without a this@ label?

Then the release question, which is the real one. This library publishes to Maven Central. Adding @DslMarker to an existing builder cannot break a binary, but it can absolutely stop a user's source compiling — so is the migration a breaking change, and if it is, what does a deprecation cycle even look like for a compile-time scope rule? ADR 0003's own answer for the spellings it deprecated is at lines 87–90; decide whether the same reasoning transfers.
