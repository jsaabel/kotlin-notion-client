04 — Coroutine primitives in anger: the rate limiter

A Mutex held across a delay, a Ktor Send hook, and a clock you are allowed to lie to · Hard

The hook

On 30 May 2026 the rate limiter was assessed rather than changed. journal/2026_05_30_01_RateLimiting_Diagnosis.md is headed "No code changes — assessment only", and its walk-through of a fan-out batch reads:

journal/2026_05_30_01_RateLimiting_Diagnosis.md:47–53 
- 100 coroutines fire simultaneously; ~3 succeed, ~97 get 429.
- All 97 enter their own retry loop with the same exponential schedule. Jitter is only
  ±10 %, so they cluster within a 200 ms window.
- After ~1 s they all retry simultaneously → ~3 succeed, ~94 fail again.
- After 1 + 2 + 4 = 7 s (≈3 retries each), only ~9 of the 100 will have succeeded.
  The other ~91 hit `MAX_RETRIES_EXCEEDED` and throw, even though the right answer was
  simply "wait longer."

Nothing there is a coding error. The backoff, the jitter and the retry ceiling were all right. What was missing was any mechanism by which a hundred coroutines could know about each other, so each reached the same conclusion at the same instant — defect #1, "no global concurrency control" (line 107). Version 0.5.0 shipped the next day; CHANGELOG.md:802–807 records ratelimit/ collapsing "from ~600 LOC across three files to 286 LOC across three files". Two decisions inside those 286 lines look like bugs on a first read.

The concept, plainly

The plugin does two unrelated jobs. Proactive throttling stops you generating 429s: outbound requests are paced so the server never has cause to complain. Reactive retry handles what you could not predict — a limit you hit anyway, a gateway that blinked, a socket that timed out. The first is a queue discipline, the second an error classifier; the diagnosis is entirely about the absence of the first.

A token bucket is the throttle. Its whole state is a fractional count of tokens, a refill rate, a ceiling, and the timestamp at which the count was last brought up to date. Sending costs one token; if there is not one, you wait. The bucket starts full, which is what gives you a burst: the first burstCapacity requests pay nothing.

The word doing the work is continuous. There is no timer and no coroutine waking every 333 ms to add a token: refill is computed lazily, when somebody asks, from elapsed time since the last computation — tokens += elapsed × rate. That is why the count is a Double. Were tokens whole, a caller arriving 200 ms into a 333 ms interval would see zero and wait a full interval, discarding credit it had already earned; discrete grants make the rate lurch and tie it to when callers arrive relative to the tick. Fractionally, the bucket holds 0.6 of a token and the caller sleeps exactly as long as the remaining 0.4 needs.

This code, annotated

refill(), and the two guards in it

src/main/kotlin/it/saabel/kotlinnotionclient/ratelimit/TokenBucket.kt:36–40 
    private val tokensPerMillis = sustainedRate / 1000.0
    private val mutex = Mutex()

    private var tokens: Double = burstCapacity.toDouble()
    private var lastRefill: Long = currentTimeMillis()
src/main/kotlin/it/saabel/kotlinnotionclient/ratelimit/TokenBucket.kt:63–70 
    private fun refill() {
        val now = currentTimeMillis()
        val elapsed = now - lastRefill
        if (elapsed > 0) {
            tokens = (tokens + elapsed * tokensPerMillis).coerceAtMost(burstCapacity.toDouble())
            lastRefill = now
        }
    }

Four fields, two mutable, one line of arithmetic. lastRefill is stamped at construction, so a client idle for an hour banks no credit, and coerceAtMost is the ceiling that makes this a bucket rather than an accumulator. The if (elapsed > 0) guard stops lastRefill advancing when no time has passed — several acquisitions inside one millisecond is normal during a burst, and a clock that has not moved must not swallow credit.

The Mutex is held across the delay

src/main/kotlin/it/saabel/kotlinnotionclient/ratelimit/TokenBucket.kt:48–61 
    suspend fun acquire() {
        mutex.withLock {
            while (true) {
                refill()
                if (tokens >= 1.0) {
                    tokens -= 1.0
                    return
                }
                val deficit = 1.0 - tokens
                val waitMillis = ceil(deficit / tokensPerMillis).toLong().coerceAtLeast(1L)
                delay(waitMillis)
            }
        }
    }

Take the reviewer's reading first; it is a good one. Standard advice is to hold a lock for as few instructions as possible; here it is held across a delay that can run a third of a second, inside a loop, so the hold can span several, blocking everyone else wanting a token. The obvious rewrite — compute waitMillis under the lock, release, sleep outside, come back — is what you would reach for in almost any lock-and-sleep situation.

That rewrite is the bug at the top of this page, rebuilt inside the throttle meant to prevent it. Waiters sleeping outside the lock all wake at roughly the same instant, having computed their delay from the same observed deficit; they race for one token, one wins, the rest recompute and sleep again. There is no ordering property at all — a coroutine can lose arbitrarily often, so the caller that arrived first may be served last, or never. Holding the lock turns the problem into a queue: the mutex's own wait list is the request queue, and waiters are handed the token in arrival order.

The cost that looks alarming is not real either. The lock is held for exactly as long as it takes to mint one token — precisely the interval in which, by definition, nobody else may send anything. Throughput is capped at that rate by construction, so none is lost, and a coroutine suspended inside withLock occupies no thread.

Two honest caveats. The KDoc's claim that acquisitions are "FIFO-fair" (TokenBucket.kt:17–18) rests on the implementation's wait queue; the current kotlinx.coroutines.sync.Mutex API documentation promises no ordering, so the property is pinned by a test rather than a contract. And the queue is strictly first-come-first-served, with no priority and no timeout on acquire:

src/test/kotlin/unit/ratelimit/TokenBucketTest.kt:69–80 
                val completionOrder = mutableListOf<Int>()
                val total = 25
                repeat(total) { index ->
                    launch {
                        bucket.acquire()
                        completionOrder += index
                    }
                }
                advanceUntilIdle()

                // No starvation: every acquirer completes, strictly in arrival order.
                completionOrder shouldBe (0 until total).toList()

Hooking Send rather than every call site

src/main/kotlin/it/saabel/kotlinnotionclient/ratelimit/NotionRateLimit.kt:114–122 
        on(Send) { request ->
            var attemptNumber = 0

            // Set once a terminal response is reached (success or a non-retryable failure); the loop
            // exits only then, so after it `result` is a guaranteed non-null call.
            var result: HttpClientCall? = null
            while (result == null) {
                // Every send — initial or retry — is paced through the bucket.
                tokenBucket.acquire()

createClientPlugin builds a plugin from a config factory and a block of hooks; Send is the outermost. A handler registered with on(Send) receives the fully-built request and must return an HttpClientCall, normally via proceed(request) — and it may call proceed more than once. That is why retry belongs here and not at a response hook: a response observer sees a call that already happened; a Send handler owns the decision to make it again. Note where acquire() sits — inside the loop, so a retry buys a token like any initial attempt. Exempting retries from your own pacing accelerates exactly when the server asked you to slow down.

Hooking the pipeline also fixes a coverage bug, not a matter of taste. Previously each API method opted in by wrapping its call, and SearchApi and FileUploadApi never had (diagnosis, lines 89–93; fix at CHANGELOG.md:767–769). A guarantee every future call site must remember is not a guarantee.

Classification by type, never by message

src/main/kotlin/it/saabel/kotlinnotionclient/ratelimit/NotionRateLimit.kt:42–44 
 * - Classifies failures by *type*, never by string-matching `error.message`: the plugin has the
 *   response object in scope, so it inspects [io.ktor.http.HttpStatusCode] and exception classes
 *   directly.

The KDoc is emphatic because its predecessor did the other thing, and the diagnosis costed it:

journal/2026_05_30_01_RateLimiting_Diagnosis.md:79–83 
- `isRetryableError` / `isClientError` / `isServerError` work by
  `error.message?.lowercase().contains("429" / "400" / "500" / …)`.
  Brittle: a 404 whose response body or URL contains "500" would be misclassified.
  Notion's JSON also uses `"code": "rate_limited"` — if we ever surface that string
  instead of `429`, classification breaks.

String-matching is what a naive catch forces on you: by then you often hold only the exception's rendered message, the status flattened into prose. The Send handler never gets there — it holds the call and reads the status as a number:

src/main/kotlin/it/saabel/kotlinnotionclient/ratelimit/NotionRateLimit.kt:149–161 
                val delayDuration =
                    when {
                        status in RETRY_AFTER_STATUSES && retriesRemaining -> retryAfterDelay(call, attemptNumber)
                        status in RETRYABLE_SERVER_STATUSES && retriesRemaining -> exponentialBackoff(attemptNumber)
                        else -> null
                    }

                if (delayDuration == null) {
                    result = call
                } else {
                    delay(delayDuration)
                    attemptNumber++
                }

RETRY_AFTER_STATUSES = setOf(429, 529) (NotionRateLimit.kt:174): both ship Notion's Retry-After, so 529 takes the header-driven path, and the header replaces the exponential schedule rather than stacking with it — lines 102–112 wait the header value plus a one-second rounding margin. The other set carries the sharper judgement:

src/main/kotlin/it/saabel/kotlinnotionclient/ratelimit/NotionRateLimit.kt:176–181 
/**
 * Server-side statuses worth retrying on the exponential schedule. `500` is deliberately excluded:
 * it usually signals a non-transient server fault rather than a transient blip, whereas `502`
 * (bad gateway), `503` (service unavailable) and `504` (gateway timeout) are typically momentary.
 */
private val RETRYABLE_SERVER_STATUSES = setOf(502, 503, 504)

Lumping all of 5xx together is the default reflex and it is wrong. 502/503/504 are statements about infrastructure, usually true for a second or two; a 500 is a statement about your request, and retrying it fetches the same exception again while delaying the error the caller needs (TypedRetryClassifierPluginTest.kt:119–149 pins exactly one attempt). Note retriesRemaining too: once retries are exhausted the guard fails and the call returns immediately rather than sleeping one unused interval — defect #5, pinned by MaxRetriesWallTimeTest:69–73 at 7,000 virtual milliseconds rather than 15,000.

The clock, and the test that guards the tests

src/main/kotlin/it/saabel/kotlinnotionclient/ratelimit/NotionRateLimit.kt:25–29 
    /**
     * Test seam: overrides the token bucket's millisecond time source so tests can drive pacing
     * with `kotlinx.coroutines.test` virtual time. `null` uses a real monotonic clock.
     */
    internal var timeSourceMillis: (() -> Long)? = null

One nullable function, internal so it is not public API, threaded into the bucket as pluginConfig.timeSourceMillis ?: { System.nanoTime() / 1_000_000 } (NotionRateLimit.kt:81). Tests pass { currentTime }. Inside runTest, delay does not sleep: the test dispatcher holds a scheduler of pending resumptions ordered by virtual instant and, when nothing is runnable, jumps the clock to the next one. The bucket would still run on its real clock there — measuring real milliseconds against skipped delays, and pacing wrongly. The injection makes the two clocks one clock.

src/test/kotlin/unit/ratelimit/VirtualTimeProbeTest.kt:49–58 
                val wallElapsed = wallStart.elapsedNow()
                val virtualElapsed = currentTime - virtualStart

                println("  Wall-clock elapsed: ${wallElapsed.inWholeMilliseconds} ms")
                println("  Virtual elapsed:    $virtualElapsed ms")

                // Virtual time advanced by sum(delays) = 7000 ms
                virtualElapsed shouldBe 7_000L
                // Wall-clock barely moved (the whole loop was simulated)
                wallElapsed.inWholeMilliseconds shouldBeLessThan 500L

VirtualTimeProbeTest tests no production code; its KDoc calls it "Investigation #4", written before the rewrite to establish that virtual time survives the shape the design would use — a retry loop with a delay inside mutex.withLock { }. The first assertion in each of its three tests is the ordinary one. The second is the interesting one: wallElapsed shouldBeLessThan 500L is not testing the loop, it is testing that the loop was simulated.

That guards a suite passing for the wrong reason. Every timing test downstream asserts a virtual duration, and all would keep passing if virtual time quietly stopped applying: MaxRetriesWallTimeTest would still see 7,000 ms elapse, because 7,000 ms really would. Nothing goes red; the suite merely becomes slow and non-deterministic while staying green, and this assertion is the only thing that fails in that scenario. The transferable move: when a test's value depends on a mechanism the test does not itself exercise — a clock that is fake, a fixture that is loaded, a mock that is wired — assert the mechanism too.

The analogy, and its limits

The mapping that holds is Guava's RateLimiter: the same bucket, the same continuous-refill arithmetic, the same fractional-permit accounting — right up to the point where Guava's acquire() parks the calling thread, which is why a JVM library cannot casually put one in front of a thread-pooled client and why this one can.

The analogy that actively misleads is the one your instincts reach for at TokenBucket.kt:49–58: a synchronized block with a Thread.sleep() in it. That really is the anti-pattern it resembles. A platform thread holding a monitor while sleeping cannot be reused, and a queue of them is a stack of parked OS resources; the compute-then-release-then-sleep advice exists because of exactly that cost. Carry the instinct into Kotlin unexamined and you will "fix" this bucket into a thundering herd. A coroutine suspended inside withLock holds a logical lock and no thread, so the only resource held is the right to be next — which is the resource the bucket exists to allocate. The point is narrower than "coroutines are cheap": rules of thumb about lock hold times are proxies for a thread cost that suspension removes, and once a proxy stops tracking its cost, the rule can invert.

One analogy to refuse: a token bucket is not a semaphore. A Semaphore(20) bounds requests in flight; the bucket bounds requests started per second and returns nothing on completion. Notion's limit is a rate — but the library therefore bounds concurrency not at all.

Exercises

Exercise 1 — Verifiable

Predict the timestamps before running. Take sustainedRate = 2.0 and burstCapacity = 3, launch eight coroutines that each acquire(), and work out from TokenBucket.kt:48–70 when each returns.

The derivation: the bucket starts with 3.0 tokens at currentTime 0, so acquisitions 1–3 decrement and return without reaching the delay. The fourth finds 0.0, so deficit is 1.0 and tokensPerMillis is 0.002, giving waitMillis = ceil(1.0 / 0.002) = 500; it sleeps, loops, refills exactly one token and takes it. Everyone after pays the same 500 ms. As a scratch spec at src/test/kotlin/unit/ratelimit/ScratchTimingProbe.kt:

@file:OptIn(kotlinx.coroutines.ExperimentalCoroutinesApi::class)

package unit.ratelimit

import io.kotest.core.annotation.Tags
import io.kotest.core.spec.style.FunSpec
import io.kotest.matchers.shouldBe
import it.saabel.kotlinnotionclient.ratelimit.TokenBucket
import kotlinx.coroutines.launch
import kotlinx.coroutines.test.advanceUntilIdle
import kotlinx.coroutines.test.currentTime
import kotlinx.coroutines.test.runTest

@Tags("Unit")
class ScratchTimingProbe :
    FunSpec({
        test("eight acquisitions at rate 2.0, burst 3") {
            runTest {
                val bucket =
                    TokenBucket(
                        sustainedRate = 2.0,
                        burstCapacity = 3,
                        currentTimeMillis = { currentTime },
                    )
                val times = mutableListOf<Long>()
                repeat(8) {
                    launch {
                        bucket.acquire()
                        times += currentTime
                    }
                }
                advanceUntilIdle()
                times shouldBe listOf(0L, 0L, 0L, 500L, 1000L, 1500L, 2000L, 2500L)
            }
        }
    })

Expected end state. ./gradlew test -Dkotest.tags.include="Unit" --tests "*.ScratchTimingProbe" goes green with exactly [0, 0, 0, 500, 1000, 1500, 2000, 2500] — no tolerance window, no range matcher. Then set sustainedRate = 3.0 and predict again: you will not get 334, 667, 1000. Work out from the ceil and the leftover fractional token why the gaps alternate. Delete the file when you are finished.

Exercise 2 — Extension

The scope of the bucket is stated as a rule, not an accident:

src/main/kotlin/it/saabel/kotlinnotionclient/ratelimit/TokenBucket.kt:20–21 
 * One bucket is created per [NotionRateLimit] plugin install — i.e. per `HttpClient` /
 * `NotionClient` — never as a process-global singleton.

Notion's limit, though, applies per integration token. Work out what breaks when one process builds two NotionClients on the same token — a read client and a write client, say. Each has a full burst of 20 and a private 3/s allowance, so the process paces itself at 6/s and believes it is behaving. Which side notices first, and what do the two then do to each other through the retry loop?

Then design the fix and be honest about where it hurts. Keying buckets by token means holding them process-wide, which is what that "never" guards against: what is the lifecycle of that map, who evicts an entry when the last client using it closes, and what happens to a consumer running two tenants' tokens in one JVM? Ask too whether the Mutex queue survives a bucket shared across clients with different cancellation semantics. And note the constraint that makes this a design question rather than a refactor: TokenBucket is internal while NotionClient construction is public API.
