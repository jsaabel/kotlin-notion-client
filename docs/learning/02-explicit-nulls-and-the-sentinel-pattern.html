02 — explicitNulls = false and the sentinel pattern

When one Kotlin null has to mean three different things · Hard

The hook

On 22 August 2026 two affordances in this library's DSL were checked against the live API, and neither did what it said. docs/adr/0002-explicit-null-payloads.md opens on the one that had been wrong the longest:

docs/adr/0002-explicit-null-payloads.md:17–22 
- **`icon.remove()` / `cover.remove()` were silent no-ops.** Notion removes an icon or cover
  when the request carries `"icon": null` —
  `reference/notion-api/documentation/endpoints/Update_Page_2025.md` is explicit ("Set to
  `null` to remove"). Both builders set the backing field to `null`, so
  `updatePageRequest { icon.remove() }` encoded to `{}` — an empty PATCH, which Notion accepts
  and does nothing with. The call compiled, ran, returned a `Page` and changed nothing.

Compiled, ran, returned a Page, changed nothing. The sibling affordance failed in the opposite register:

docs/adr/0002-explicit-null-payloads.md:23–31 
- **Clearing a property value threw.** Seven `PagePropertiesBuilder` setters document "null for
  empty" and construct a value object whose payload field is `null`: `select`, `status`,
  `date`, `dateTime`, `number`, `url`, `email`, `phoneNumber`. Notion clears a property when it
  receives `{"Status":{"select":null}}`; the encoder emitted `{"Status":{"type":"select"}}` —
  the discriminator survived, the instruction did not. Notion **rejects** that shape with HTTP
  400 `validation_error`, listing every payload key it would have accepted
  ("`body.properties.Stage.select should be defined, instead was undefined`"), and leaves the
  property at its previous value. This half was a loud failure, not silent data loss — no
  caller can have been depending on it.

One root cause, two failure modes, kept apart because they justify the fix differently — "one is a change the caller cannot see not happening, the other is a call that never worked at all" (lines 33–34 of the same ADR). Then the finding this lesson is really about:

docs/adr/0002-explicit-null-payloads.md:36–41 
Neither was visible to the test suite, and that is the more interesting half of the finding.
`UpdatePageRequestBuilderTest` asserted `request.icon shouldBe null` after `icon.remove()` —
byte-identical to the assertion for a request that never mentioned the icon. Every affected
path had a **passing model-level test**, including the ones whose live call would have thrown.
The bug lives entirely between the model and the wire, so only an assertion on encoded bytes
can see it.

That is a class of bug, not an incident, and it deserves a name. An assertion on a model and an assertion on the wire are different tests, and only the second is testing serialization. Everything between your objects and the bytes — a custom serializer, a naming strategy, a global include-or-omit setting — is code no model-level assertion reaches. Every affected path here had a passing test, including the ones that earned a 400.

The concept, plainly

Notion's page update is a merge patch in all but name: the body carries the fields you are changing and nothing else. The reference is explicit about what a null inside it means:

reference/notion-api/documentation/endpoints/Update_Page_2025.md:27–28 
| `icon` | object \| null | Set page icon (emoji, external URL, file upload, or custom emoji). Set to `null` to remove. |
| `cover` | object \| null | Set page cover (file upload or external URL). Set to `null` to remove. |

So the wire carries two instructions that both involve the word null. Key absent means leave the icon alone; key present, holding JSON null means delete it. Kotlin has one null, and val icon: Icon? = null has to express both.

explicitNulls = false resolves that globally, in favour of the common case: a null field is omitted. For a request layer of one nullable field per optional input that is what makes a PATCH a PATCH — otherwise every updatePageRequest { } sends null for every field the caller never touched, and Notion reads those as instructions.

Count the meanings one null now carries. Absent from this request: never set, drop it. Set this to JSON null: set deliberately, to the removal instruction. The API returned null: this page has no icon. Three meanings, one representation, and the encoder always picks the first. It is not making a mistake; it is answering a question that was never asked properly.

The fix is not to change the encoder's mind, per field or globally. It is to stop asking it a question it cannot answer:

docs/adr/0002-explicit-null-payloads.md:48–51 
Model an intended `null` as a **value**, not as the absence of one. A Kotlin `null` on a
nullable request field keeps its single, honest meaning — "this request says nothing about that
field" — and anything that must reach the wire as `null` is a non-null Kotlin value whose
serializer writes `null` on purpose. `explicitNulls = false` then never has a decision to make.

Once "remove the icon" is a value — a non-null Icon whose serializer writes null on purpose — the nullable field goes back to one meaning, and untouched-versus-cleared becomes visible to the type system instead of buried in an encoder setting. That is the pattern; the rest is where to put it.

Where the setting lives

src/main/kotlin/it/saabel/kotlinnotionclient/serialization/NotionJson.kt:15–19

One Json instance, internal, built in one place (NotionJson.kt:21–29) so tests assert against the configuration the client installs — and its KDoc states the rule and its exception in one breath.

The one method that does the dropping

src/main/kotlin/it/saabel/kotlinnotionclient/models/pages/PageRequests.kt:75–82 
@Serializable
data class UpdatePageRequest(
    @SerialName("properties")
    val properties: Map<String, PagePropertyValue>? = null,
    @SerialName("icon")
    val icon: Icon? = null,
    @SerialName("cover")
    val cover: PageCover? = null,

Every field there is nullable with a null default, so the plugin-generated serializer writes each one with encodeNullableSerializableElement. That name matters more than anything else in this lesson. CompositeEncoder offers two ways to write a structure member, and kotlinx's JSON encoder overrides only one: StreamingJsonEncoder declares encodeNullableSerializableElement, which skips the element entirely when the value is null and explicitNulls is off. It does not declare encodeSerializableElement at all — that one is inherited from AbstractEncoder, which writes the key and hands the value to the serializer it was given. javap -p on kotlinx-serialization-json-jvm-1.11.0.jar shows exactly that.

So the whole fix is a choice between two overloads, re-derivable from one question: which method has the authority to write nothing? Only the nullable one. Anything that must reach the wire travels a route where that decision is never taken — hold a non-null value, or go through encodeSerializableElement with a serializer that accepts nulls. This repo uses both, one per failure mode.

Route one: a value that exists in order to be written as null

src/main/kotlin/it/saabel/kotlinnotionclient/models/base/Icon.kt:130–133 
    @Serializable(with = IconRemovedSerializer::class)
    data object Removed : Icon() {
        override val type: String = "removed"
    }
src/main/kotlin/it/saabel/kotlinnotionclient/serialization/ExplicitNullSerializers.kt:38–47 
internal abstract class RemovalSentinelSerializer<T : Any>(
    serialName: String,
) : KSerializer<T> {
    override val descriptor: SerialDescriptor = buildClassSerialDescriptor(serialName)

    @OptIn(ExperimentalSerializationApi::class)
    override fun serialize(
        encoder: Encoder,
        value: T,
    ) = encoder.encodeNull()

The descriptor has no elements — honest, since nothing is ever written through it; its name is "for diagnostics only" (line 36), and serialize is one encodeNull(). icon.remove() sets iconValue = Icon.Removed (UpdatePageRequestBuilder.kt:319–321), so the field holds a non-null value: encodeNullableSerializableElement has no decision to make and delegates, and the serializer writes the null the encoder would otherwise have written for the wrong reason. The sentinel is write-only — deserialize throws (lines 49–53), because a removed icon reads back as an ordinary Kotlin null (ADR 0002, lines 108–109).

Route two: keep the key, whatever the payload

src/main/kotlin/it/saabel/kotlinnotionclient/models/pages/PageRequests.kt:214–219 
    @Serializable(with = SelectValueSerializer::class)
    @SerialName("select")
    data class SelectValue(
        @SerialName("select")
        val select: SelectOption?,
    ) : PagePropertyValue() {

PagePropertyValue is a plain @Serializable sealed class (PageRequests.kt:104–105), so "type" is the class discriminator kotlinx's polymorphic layer injects, while "select" is written by the variant's own element serializer. Two different pieces of code write those two keys — which is why the old bug produced {"type":"select"} and not {}: the discriminator survived because whatever dropped the payload had no say over it.

src/main/kotlin/it/saabel/kotlinnotionclient/serialization/ExplicitNullSerializers.kt:70–80 
internal abstract class ClearableValueSerializer<T : Any, P : Any>(
    serialName: String,
    payloadKey: String,
    payloadSerializer: KSerializer<P>,
) : KSerializer<T> {
    private val nullablePayloadSerializer: KSerializer<P?> = payloadSerializer.nullable

    override val descriptor: SerialDescriptor =
        buildClassSerialDescriptor(serialName) {
            element(payloadKey, nullablePayloadSerializer.descriptor)
        }
src/main/kotlin/it/saabel/kotlinnotionclient/serialization/ExplicitNullSerializers.kt:88–95 
    override fun serialize(
        encoder: Encoder,
        value: T,
    ) = encoder.encodeStructure(descriptor) {
        // encodeSerializableElement, not encodeNullableSerializableElement: the latter is where
        // explicitNulls = false drops the key. The nullable serializer writes the null instead.
        encodeSerializableElement(descriptor, 0, nullablePayloadSerializer, payloadOf(value))
    }

The comment is the lesson, put where whoever changes the line will read it. The payload serializer is wrapped once with .nullable: a KSerializer<P> becomes a KSerializer<P?> that writes encodeNull() rather than refusing a null. The descriptor declares one element, and buildClassSerialDescriptor gives it CLASS kind — which the polymorphic encoder needs in order to inject "type".

serialize then writes that element with encodeSerializableElement and the KSerializer<P?>: the key goes out unconditionally, and the null, when there is one, is written by the nullable serializer. A cleared value and a set one now differ only in the payload — which, as the KDoc notes at line 64, "also matches what Notion sends on the way in". Subclasses supply payloadOf and withPayload. There are seven:

Seven serializers for the eight setters the ADR lists, because date and dateTime both build a DateValue. The header's last paragraph is what stops the pattern spreading: list-valued properties clear with [], which is not a null. The ADR also turned down the generalisation — one serializer over the whole property map — as "fix-up-at-a-distance": "a reader of SelectValue sees a nullable field with no hint that its null is load-bearing" (lines 89–93).

JsonContentPolymorphicSerializer gives encoding away free: implement selectDeserializer, and on the way out it resolves the runtime class's serializer reflectively — the right price for most of this hierarchy, and the decode half still uses it (lines 31–47). But Icon.Removed is a data object, and a reflective lookup for an object variant can land on the generic object serializer, which writes {}. Not a crash: an icon field set to an empty object — the silently wrong payload the ADR exists to remove, reintroduced by the mechanism meant to fix it. The explicit when also buys exhaustiveness. PageCoverSerializer.kt:48–59 is the same.

Why not just flip the switch

docs/adr/0002-explicit-null-payloads.md:80–85 
- **Flip `explicitNulls` to `true` and model absence explicitly.** Semantically the more honest
  model, and it removes the *cause* rather than the instances. Rejected on blast radius: every
  `?= null` field in every request model would start serializing as `null` unless individually
  wrapped in an absence type, which is a rewrite of the whole request layer to fix two known
  sites. The sentinel mechanism is itself reusable, so a third instance is cheap — and if the
  request layer is ever reshaped for other reasons, this decision is worth revisiting.

A clean worked example of scoping a fix. The rejected option is conceded to be better — it "removes the cause rather than the instances" — and rejected anyway on blast radius: two known sites against every nullable field in every request model, each needing an absence wrapper. Not a fix; a rewrite with a fix inside it.

Two details make that honest rather than merely convenient. It names the condition under which the decision expires — "if the request layer is ever reshaped for other reasons, this decision is worth revisiting". And it records the obvious per-field escape hatch, and why it is not one:

docs/adr/0002-explicit-null-payloads.md:86–88 
- **`@EncodeDefault` on the nullable payload fields.** Does not work: `explicitNulls = false`
  drops a null nullable field in `encodeNullableSerializableElement`, independently of whether
  the value is a default.

The same distinction from the other side: the check lives in encodeNullableSerializableElement, not in whatever decides defaults, so an annotation about defaults cannot reach it.

The analogy, and its limits

The Jackson instinct is right about the setting and wrong about the fix. @JsonInclude(Include.NON_NULL) is the same policy, and if you have configured it on an ObjectMapper you have shipped this bug's cousin. But Jackson's inclusion is per property and overridable: annotate one field Include.ALWAYS and it opts back in. Reaching for that here costs the afternoon. explicitNulls belongs to the Json instance and has no per-property override; @EncodeDefault is about defaults, and the check is not there. That absence is why the fix has to be a type.

The second analogy holds better. A patchable field is a three-state field — absent, null, present — and the ecosystem's usual answer is a wrapper: JsonNullable<T> from the OpenAPI generators, or a hand-rolled Undefined | Null | Value. This repo reached the same three states more cheaply, pushing the extra state into a type that was already sealed. Where that stops: only where the field's type is yours to extend. Icon could gain Removed; a field declared String? cannot, which is why the clearable values needed the other route. The two are not stylistic variation.

And a sentinel is not free at the boundary: adding a variant to a public sealed hierarchy is a source-breaking change for any exhaustive when in user code (ADR 0002, lines 104–107), where a wrapper would have been additive. Cheap here only because nothing matched exhaustively — checked, not assumed.

See it yourself

This runs against the repo as it stands, hits no network, and takes about a second:

./gradlew test -Dkotest.tags.include="Unit" --tests "*.ExplicitNullPayloadSerializationTest"

Read the test file beside the output — twenty-odd assertions, all on strings. Then break it on purpose: in src/main/kotlin/it/saabel/kotlinnotionclient/models/pages/PageRequests.kt, delete line 164, the @Serializable(with = NumberValueSerializer::class) on NumberValue, so the variant falls back to its plugin-generated serializer. Re-run. The cleared-number case now reports an actual of {"properties":{"P":{"type":"number"}}} — the discriminator without the instruction, the payload Notion answers with a 400. One deleted annotation is the entire bug.

Exercises

Exercise 1 — Verifiable

Pin the old, broken payload for one of the seven clearable setters, watch it fail, then correct it. Use number.

  1. Write a fresh Kotest FunSpec, tagged @Tags("Unit"), encoding updatePageRequest { properties { number("P", null as Double?) } } with NotionJson.default. The cast picks the nullable overload (PagePropertiesBuilder.kt:165–170).
  2. Assert on the model first: request.properties!!["P"] shouldBe PagePropertyValue.NumberValue(number = null). Green — and green before the fix too.
  3. Now assert on the bytes, pinning the pre-fix payload: {"properties":{"P":{"type":"number"}}}.

Expected end state. Step 3 fails, and the message is the lesson: expected {"properties":{"P":{"type":"number"}}}, actual {"properties":{"P":{"type":"number","number":null}}}. Change the expectation to the actual and it goes green. The assertion has moved from "the field is null" — true in both worlds, therefore worthless — to "the encoded bytes are {"properties":{"P":{"type":"number","number":null}}}", false in exactly one.

Then earn the failure back. Delete PageRequests.kt:164 and re-run: your corrected assertion now fails with the old bytes as the actual. Restore the line.

Exercise 2 — Extension

ADR 0002 claims "the sentinel mechanism is itself reusable, so a third instance is cheap" (lines 84–85). Test that by designing the third instance for a case the repo does not handle: deleting a property from a data source schema. DataSourceRequestBuilder.kt:359–360 tells callers to remove a property by simply not including it — check that against the API before believing it, and notice the claim's shape.

Three places it strains. The intended null sits in a map value, not a class member — so which encoder method does a Map serializer use for its values, and does explicitNulls reach it at all? That answer may make the sentinel unnecessary, or impossible. Second, the variant would live on DatabaseProperty, which is also decoded from responses — what keeps it out of a schema someone read back? Third, deleting a property destroys data, and the ADR's rejected fourth option was to document the raw request instead. Is this where that one is right?
