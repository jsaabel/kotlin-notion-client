01 — The wire is the contract

kotlinx.serialization past @Serializable · Medium

The hook

On 3 November 2025 a query against a live workspace started failing, and the client reported this:

Network error occurred

Nothing was wrong with the network. journal/2025_11_03_Unsupported_Property_Types_Investigation.md records the reproduction:

journal/2025_11_03_Unsupported_Property_Types_Investigation.md:10–13 
### Reproduction
1. Query data source with standard properties → ✅ Works
2. Add button property to any page → ❌ Fails with "Network error occurred"
3. Remove button property → ✅ Works again

A Notion button property holds no data at all — its JSON value is {} — and adding one to a single page took down the whole query result. The message was misleading because DataSourcesApi.kt caught bare Exception and wrapped it as NotionException.NetworkError (same journal, lines 63–66); the real failure was a SerializationException.

Six months later the same failure resurfaced one level up, on database property schemas, and that journal caught the real exception verbatim:

journal/2026_05_03_01_DatabaseProperty_Unknown_Fallback.md:12–15 
Serializer for subclass 'button' is not found in the polymorphic scope of 'DatabaseProperty'.
JSON input: {"id":"A%5E%3Bf","name":"Create schedule","description":null,"type":"button","button":{}}

That sentence is the whole lesson. @Serializable on a sealed class buys a closed world: a fixed table of subtypes, resolved by name, no default arm. Notion's API is someone else's schema on someone else's calendar, and this library has to survive the parts that did not exist when the jar shipped.

The concept, plainly

Notion's JSON is a tagged union with an unusual tag, drawn by the KDoc atop src/main/kotlin/it/saabel/kotlinnotionclient/models/pages/PageProperty.kt:

src/main/kotlin/it/saabel/kotlinnotionclient/models/pages/PageProperty.kt:25–33 
 * ## Structure Differences
 * API responses include metadata that requests don't:
 * ```json
 * {
 *   "id": "property_id",           // ← Metadata (response only)
 *   "type": "property_type",       // ← Metadata (response only)
 *   "{property_type}": { ... }     // ← Actual value
 * }
 * ```

The value of "type" is not merely a type name. It is the name of another key in the same object — {"type":"number","number":42}, {"type":"select","select":{…}}.

kotlinx.serialization's built-in polymorphism does something adjacent, which is what makes this confusing. A sealed hierarchy annotated @Serializable gets a compiler-generated SealedClassSerializer; JSON writes a class discriminator key — literally "type" by default — holding the subclass's serial name, then writes that subclass's fields flat alongside it. Squint and you get {"type":"number","number":42}, exactly what Notion sends.

Two things break.

The world is closed. The generated serializer looks the discriminator value up in a fixed table and throws when it misses — the 'button' is not found in the polymorphic scope message above. There is no "and otherwise". Every property type Notion ships after your release is a crash in a jar already on Maven Central.

The discriminator is metadata; here the tag is data. These models declare abstract val type: String — the tag is a field callers read. kotlinx refuses that combination outright: a subclass carrying a property serialized under the discriminator's name fails, and the message offers three ways out — change the discriminator in JsonConfiguration, rename the property, or fall back to array polymorphism. When the wire format is someone else's, none is available.

Nor does the Json configuration rescue this. The 2025 journal, lines 68–70: ignoreUnknownKeys = true "only ignores unknown JSON keys, NOT unknown sealed class subtypes". Leniency about extra fields and leniency about unmodelled variants are different features, and this library needs both.

So the serializer is written by hand. A KSerializer<T> is three members: descriptor, serialize, deserialize. The technique that makes Notion's shape tractable is to stop streaming: cast the Decoder to a JsonDecoder, pull the subtree into a JsonElement, read the tag from the materialised tree, then hand the same element to whichever generated serializer you chose. You pay a tree allocation and lose incremental decode; in exchange you can construct a value no generated serializer would have produced.

@Serializable(with = …) is the switch: the compiler still generates a serializer per variant, which is what PageProperty.Number.serializer() resolves to, but the base class delegates to the hand-written one. Note what that does to @SerialName("number") — it no longer drives dispatch, which is now a when over a String; the annotation survives as documentation. Meanwhile type is an ordinary modelled field, the collision kotlinx would have rejected.

Four decisions in fifteen lines. require(decoder is JsonDecoder) states the format dependency up front rather than failing later with a ClassCastException. decodeJsonElement() is the pivot from streaming to tree. A missing "type" is fatal — the library will not guess a variant from the payload's shape. id is read generically, because the one branch that cannot delegate needs it by hand.

Then twenty-three branches of one form — decoder.json.decodeFromJsonElement(PageProperty.X.serializer(), element), re-dispatching the same parsed element. Then the branch the whole file exists for:

The distinction that costs an hour if you miss it

The serializer's KDoc spends four lines on a difference that is not about mechanics, but about who has to fix the problem:

src/main/kotlin/it/saabel/kotlinnotionclient/models/pages/PagePropertySerializer.kt:38–41 
 * [PageProperty.Unknown] means *this client* does not model the type. It is not the same as
 * Notion reporting that it could not compute a value: the API's own `"unsupported"` formula and
 * rollup values are modelled explicitly as [FormulaResult.UnsupportedResult] and
 * [RollupResult.UnsupportedResult].
src/main/kotlin/it/saabel/kotlinnotionclient/models/pages/PageProperty.kt:339–357 
    /**
     * Notion could not compute this formula, so it returned no value.
     *
     * The API reports `formula.type = "unsupported"` with an empty `unsupported`
     * object when a formula depends on too many related pages or on too deeply
     * nested formulas and rollups. This says nothing about this client's support
     * for the property — the formula is visible in Notion's UI but the API
     * declines to evaluate it — so it is a workspace-side limit to work around
     * (simplify the formula, or reduce the number of related pages), not a
     * missing model. Contrast [PageProperty.Unknown], which *is* a gap here.
     *
     * @property unsupported Always an empty object; kept so the value round-trips.
     */
    @Serializable
    @SerialName("unsupported")
    data class UnsupportedResult(
        @SerialName("type") val type: String,
        @SerialName("unsupported") val unsupported: JsonObject = JsonObject(emptyMap()),
    ) : FormulaResult()

Both read, at a call site, as "we don't support this". They are opposites. Unknown is a gap in this library and the fix is a pull request; Notion's "unsupported" is Notion declining to evaluate a formula, and the fix is in the workspace — simplify the formula, cut the relation count. Collapse them into one thing and you will spend an afternoon adding a variant for a type that already had one. unsupported keeps its always-empty JsonObject: worthless to read, kept so the value round-trips.

The split repeats one level down: FormulaResult and RollupResult each carry UnsupportedResult and their own Unknown, and RollupResult adds IncompleteResult for a rollup still being computed (PageProperty.kt:429–451). Three owners of three problems, all once one JsonDecodingException.

serialize, and the exhaustive when

src/main/kotlin/it/saabel/kotlinnotionclient/models/pages/PagePropertySerializer.kt:163–171, 266–273

Twenty-four near-identical branches, and no else. That absence is the enforcement point: add a variant to PageProperty and the compiler stops you here, before any test runs — the payoff the sealed hierarchy was bought for.

It is narrower than it looks, because the same hierarchy is matched elsewhere with an opt-out:

src/main/kotlin/it/saabel/kotlinnotionclient/models/pages/PageExtensions.kt:260–268

}

getPlainTextForProperty accepts new variants silently and returns null; today Files, Verification and Unknown land there. Exhaustiveness is not a property of a sealed class but of each when written over it, and one else forfeits it for that site forever.

One more thing hides in that Unknown branch: it encodes through Unknown's generated serializer, writing its three declared fields, so a decoded button property re-encodes as {"id":"…","type":"button","rawContent":{"id":"…","type":"button","button":{}}} — a shape no Notion endpoint accepts. Harmless in practice, because requests use a different hierarchy: PagePropertyValue in src/main/kotlin/it/saabel/kotlinnotionclient/models/pages/PageRequests.kt:105 (naming convention at PageProperty.kt:20–21). That is the second exercise.

Two other serializers, and why three approaches coexist

src/main/kotlin/it/saabel/kotlinnotionclient/models/base/ParentSerializer.kt:27–42 
object ParentSerializer : JsonContentPolymorphicSerializer<Parent>(Parent::class) {
    override fun selectDeserializer(element: JsonElement): DeserializationStrategy<Parent> {
        val type =
            element.jsonObject["type"]?.jsonPrimitive?.content
                ?: throw SerializationException("Missing 'type' field in Parent JSON")

        return when (type) {
            "page_id" -> Parent.PageParent.serializer()
// …
            else -> throw SerializationException("Unknown Parent type: $type")
        }
    }
}

JsonContentPolymorphicSerializer is the cheap version of the same idea: kotlinx parses the element and asks one question — which strategy? One method, and encoding comes free (it serializes with the concrete class's own serializer — flat, no discriminator injected). Seventeen lines instead of two hundred and seventy-five.

The cost is the return type. selectDeserializer must return a DeserializationStrategy<Parent>; it cannot return a value. There is no way to say "build an Unknown holding this element" — the element is in your hand and the signature will not let you keep it. That is why PagePropertySerializer is a full KSerializer and ParentSerializer is not. The 2025 journal names the asymmetry as known at the time (lines 76–80: "Both currently throw on unknown types, but we'll improve this"); "agent_id" in that when is evidence Notion does add parent types.

IconSerializer is the third shape: content-polymorphic for decode, explicit dispatch for encode.

src/main/kotlin/it/saabel/kotlinnotionclient/models/base/IconSerializer.kt:25–28 
 * Encoding dispatches on the subclass explicitly rather than looking its serializer up
 * reflectively, so [Icon.Removed] reliably reaches [IconRemovedSerializer] and is written as
 * JSON `null` — a reflective lookup would fall back to the generic object serializer and emit
 * `{}` instead. See `docs/adr/0002-explicit-null-payloads.md`.

Here it is encoding that has a requirement the free implementation cannot meet, so the class keeps JsonContentPolymorphicSerializer as a private nested ContentSerializer for decoding (IconSerializer.kt:31–47) and hand-writes only serialize. Icon.Removed and Icon.PendingUpload appear only in the encode when — request-side variants that never arrive from Notion.

Three serializers, three amounts of hand-written code, tracking exactly one thing: which side of the round trip has a requirement the generated machinery cannot express.

One Json, in one place

src/main/kotlin/it/saabel/kotlinnotionclient/serialization/NotionJson.kt:6–12, 21–29 
 * The JSON configuration every request the client sends is encoded with.
 *
 * Kept in one place so tests can assert on the *exact* bytes a request produces rather than on a

// …

internal object NotionJson {
    /** Builds the client's JSON configuration. @param prettyPrint indent the encoded output */
    fun forClient(prettyPrint: Boolean = false): Json =
        Json {
            ignoreUnknownKeys = true
            this.prettyPrint = prettyPrint
            encodeDefaults = true
            explicitNulls = false
        }

The object exists so that a test asserting on encoded bytes asserts about the configuration the client actually installs (NotionClient.kt:152), not a drifted copy. It is internal on purpose: the config is not public contract, only its output is.

The analogy, and its limits

If your instinct here is Jackson-shaped, it is right and the API is missing. Jackson models Notion's exact shape as a first-class feature: @JsonTypeInfo(use = Id.NAME, include = As.EXISTING_PROPERTY, property = "type", visible = true) plus @JsonSubTypes. EXISTING_PROPERTY means "the tag is a real field, don't synthesise one"; visible = true adds "and deserialize it into the object too" — precisely the collision kotlinx rejects. And @JsonTypeInfo(defaultImpl = …) is PageProperty.Unknown in an annotation.

Where the analogy stops. Jackson can do that because it reflects over your classes at runtime; kotlinx generates serializers at compile time and never looks at a class again, so there is nowhere for a "when unrecognised, construct this" hook to live. The nearest thing it offers is SerializersModule.polymorphicDefaultDeserializer, which does not reach this case: the provider is handed the discriminator string only — (String?) -> DeserializationStrategy<T>? — and returns a strategy, not a value. It can route an unknown tag; it cannot preserve rawContent, because it never sees the JSON.

A second limit, in the code itself. buildClassSerialDescriptor("PageProperty") builds a descriptor with no elements. A descriptor is the format's map of a value; this one is a stub, and works only because both paths bypass it — decoding goes through JsonElement, encoding delegates to the variant's own generated serializer. Point CBOR or protobuf at this hierarchy and there is nothing to work from. The require(decoder is JsonDecoder) is honest about that; the descriptor is not.

A third limit, from being a library. Every variant added to a public sealed class is a source-breaking change for anyone with an exhaustive when over it. This library has done it deliberately, and says so:

CHANGELOG.md:138–143 
- **`FormulaResult` and `RollupResult` gained an `UnsupportedResult` subclass** (#36). An
  exhaustive `when` over either sealed class with no `else` branch no longer compiles.
  *This fixes a latent crash:* Notion returns `type: "unsupported"` for formulas and rollups
  that depend on too many related pages, and the missing subclass previously failed
  deserialization of the **entire page** with `JsonDecodingException`. Runtime behaviour for
  input that already worked is unchanged.

The exhaustive when is a gift inside the library and a bill outside it; that argument belongs to lesson 06.

Exercises

Exercise 1 — Verifiable

Promote button from Unknown to a real variant, end to end.

  1. Add a Button variant to PageProperty in src/main/kotlin/it/saabel/kotlinnotionclient/models/pages/PageProperty.kt, following Verification at lines 270–276. The wire payload is an empty object, so model it as JsonObject.
  2. Add the "button" branch to deserialize and the is PageProperty.Button branch to serialize in PagePropertySerializer.kt.
  3. Write the decode test in the inline-JSON style of src/test/kotlin/unit/properties/PagePropertyUnknownTypeTest.kt.

Expected end state. Your new test passes — and three existing assertions in PagePropertyUnknownTypeTest.kt (lines 89–90, 141, 177) now fail, because they pin button to Unknown. That failure is the proof your branch is live; update them.

Then predict before you run. Delete only the "button" branch from deserialize. Which fails, and how? Answer: it still compiles — the when in deserialize is over a String and has an else — and your test fails at runtime, with Kotest reporting that the value was a PageProperty.Unknown where PageProperty.Button was expected. Now put it back and delete the is PageProperty.Button branch from serialize instead. That one does not compile: 'when' expression must be exhaustive, naming the missing branch. Two deletions, two entirely different failure modes, and only one of them was caught by the type system.

Exercise 2 — Extension

Make Unknown re-encode losslessly — a decoded button property should encode back to the bytes Notion sent, not to {"id":…,"type":…,"rawContent":{…}}. Writing it is short: give Unknown its own KSerializer that emits rawContent directly. Deciding whether to is the exercise.

Consider: rawContent is response JSON, carrying id and computed values Notion rejects on write, so a faithful round trip is still not a legal request body. Does lossless re-encoding buy anything real, then, or only make an illegal payload look plausible? Would it be better to make PageProperty refuse to encode at all — the way Icon.PendingUpload does via PendingUploadRefusingSerializer — letting the type system say "responses are not requests"? What would that break for someone caching a Page as JSON?
